# 账号 TXT 宽提取与严格入库

## 目标

让账号 TXT 可以包含说明文字、JSON、Cookie、请求头和多条记录。系统从中提取账号凭据候选，逐条校验和去重；界面、列表与日志仅显示邮箱和数量，不显示 token 原文。

## 输入与提取

- JSON：提取对象或数组中的 `accessToken`、`sessionToken`，并关联同对象的 `user.email` 或 `email`。
- 键值文本：提取 `accessToken`、`sessionToken`、`__Secure-next-auth.session-token` 的 `:` 或 `=` 赋值。
- 请求头：提取 `Authorization: Bearer <token>`。
- 混排文本：提取独立的 JWT / session-token 候选；候选带来源行号或区块编号。
- 同一文件可含多个候选；提取器不能将不相关文本、错误候选或一条错误记录导致的失败扩散到其他候选。

## 标准化与本地校验

- 输出固定对象：`{ accessToken? | sessionToken?, user: { email } }`。
- 账号必须包含一个 token；token 按预期结构、长度与字符集做本地格式校验。
- 有邮箱时校验基础邮箱格式；缺少邮箱的结构正确凭据仍可入库，显示为“待识别账号”。
- 不在导入阶段发起任何外部验证、兑换或请求。
- 相同 token 通过单向摘要去重；同邮箱不同 token 可以同时保存。

## 存储与展示

- 每条有效候选独立写入资源库，保留来源文件和行/区块编号。
- 失败结果仅包含来源位置和通用原因，例如“token 格式无效”或“缺少可识别凭据”；不得包含原始行、token、Cookie 或请求头。
- 账号库、选择弹窗、任务状态只显示邮箱（或“待识别账号”）、导入时间和状态。
- 用户明确选择一条资源后，才允许业务层读取该条凭据；远端有效性由实际业务操作自行处理。

## 验收

1. 混排 TXT 可提取 JSON、Cookie、Bearer 和键值形式的多个合法候选。
2. 无效片段不阻止其他合法候选导入，且不会在响应或日志中泄露凭据。
3. 重复 token 只保留一条；同邮箱不同 token 不覆盖。
4. 导入与列表接口均不返回 token；选择接口按明确 ID 返回一条记录。
5. 浏览器抽屉显示新增、重复、无效数量与安全的原因摘要，账号展示仅为邮箱。
