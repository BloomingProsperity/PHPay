## Backend fixes

### Effective account credential

账号状态检测和支付必须共享同一个“有效账号上下文”。如果初始 access token 被拒绝，
而 session token 换取的新 token 可用，则状态检测返回并缓存新 token。支付和链接生成
必须使用新 token，不能继续使用被拒绝的旧 token。

### Stable account identity and payment completion

账号资源以稳定身份合并，优先使用规范化邮箱；缺少邮箱时才使用凭证摘要。重新导入同一
账号时更新凭证和状态，不创建第二个可支付资源。

支付完成索引独立持久化，至少保存稳定账号键、目标套餐、任务号、实际金额、币种和完成
时间。删除或清空账号库不能删除完成索引。再次导入同一账号时必须恢复完成状态，防止
重复支付同一目标套餐。

### Unified account import

粘贴和文件导入共享同一解析、状态检测、去重和拒绝逻辑。结构错误或凭证明确无效的记录
不入库；网络或验证服务暂时失败的记录保留为可重新检测的 error 状态，不误删。

### Unknown and 3DS task lifecycle

`unknown` 任务不允许自动重新提交付款。单笔和批量页面都提供逐条安全复核。复核后只能
进入 succeeded、failed、pending_3ds 或继续 unknown。

3DS 任务支持显式取消。取消只终止本地观察、将任务标记为 failed/cancelled，并释放账号、
卡、地址、代理和指纹；绝不再次提交付款。账号资源缺失或凭证失效时，UI 显示可取消状态，
不再永久无反馈悬挂。

### Address behavior

地址库为空且用户未手动填写地址时，点击单笔操作前生成一条本次临时地址。页面启动时
不得用 `config/address.json` 预填字段来绕过这条规则。临时地址默认不入库，只有用户点击
保存才入库。

### Proxy, timeout, and ownership

账号导入检测、支付任务和 3DS 检测都使用同一代理占用协调器。支付任务的代理为硬锁；
非任务状态检测不得抢占已锁定代理。

网络错误必须检查顶层错误和 cause 链，将代理连接、超时、TLS 连接等传输错误规范为
`proxy_connection_failed`。Stripe 和验证测试请求设置明确超时，超时发生在确认前才允许
按后端策略换代理，确认后保持 unknown 并等待复核。

### Link task transport

session 内容不得放入 URL。单笔和批量链接生成改用 POST 任务接口，保留现有进度和结果
展示。旧 GET/SSE 路径停用，不再读取凭证查询参数。

### Runtime cleanup and recovery

批量运行完成后关闭代理协调器并从活动 Map 移除。单笔任务释放代理时关闭其独立协调器。
恢复逻辑遍历全部未决任务，而不是只取最近 1000 条；无法对应任何未决任务的陈旧资源锁
在启动时安全释放。

## UI behavior

### Resource library

三张资源卡显示真实数量。主操作为绿色导入按钮，次操作为白色查看按钮。清空和单条删除
保留在库弹窗中。弹窗展示安全字段，不回显完整 token 或 CVC。

### Payment task

左栏是账号输入、检测结果和获取方法；右栏是套餐、并发和账号/卡/地址选择摘要。手动卡
和地址保持折叠。四个任务按钮位于卡片底部，顺序和样稿一致。

### Services and verification

验证配置、代理和 3DS 在桌面端等高三列展示。窄屏按顺序堆叠。3DS 列表只显示账号和
状态；点击账号打开详情弹窗，展示安全卡信息、支付链接、等级和检测时间。

### Task status

任务状态横跨页面底部。左侧日志，右侧成功列表。进度条显示真实百分比。批量任务同时
显示总数、排队、处理中、成功、失败、3DS、unknown 和资源等待数量。

## Safety and error handling

- 后端是重试动作的唯一权威；前端只执行返回的 `retryAction`。
- confirm 或 approve 开始后，任何传输异常都不能自动提交新付款。
- 卡余额不足会标记并停用；卡资料错误或明确拒付按既有策略切换下一张卡。
- 地址错误可换地址，不让可用卡进入冷却。
- 所有外链仅允许 HTTPS，并使用 `noopener noreferrer`。
- 公共接口只返回脱敏账号、卡尾号和安全错误码。

## Testing and verification

实现采用定向 TDD：

1. 每个后端问题先增加最小失败测试并确认失败原因；
2. 实现最小修复后只运行对应测试文件；
3. UI 先增加结构、ID、接口接线和弹窗行为断言；
4. 使用拦截接口验证单笔、批量、3DS、代理和导入行为；
5. 不调用真实账号、不生成真实结账、不提交真实付款；
6. 完成全部目标后重建 Docker；
7. 在右侧页面检查桌面和窄屏布局、控制台错误、溢出和所有关键按钮；
8. 最后只进行一次覆盖受影响模块的综合验证。

## Scope exclusions

- 不改变套餐价格和外部支付协议；
- 不新增 TLS 指纹轮换策略；
- 不真实扣款；
- 不添加样稿之外的新功能；
- 不为了样式重写已稳定的解析器、支付协议或指纹提供器。
